# RISC-V64 port: TCC + musl — done, three real bugs found and fixed

## Scope decision, settled by toolchain support, not preference

RV64, not RV32: TCC has only `riscv64-{gen,link,asm}.c` — no RV32 backend
anywhere in the source. musl has only `arch/riscv64`. RV32 would mean
writing both a compiler backend and a libc port from scratch.

## The assembler question — corrected mid-stream

Original plan was a full RV64I assembler in TCC (~600 lines, modeled on
`i386-asm.c`). Directly challenged: **why, if codegen is already direct
and intrinsics exist?** Testing the claim rather than defending it
showed two of the three justifications were wrong:

- Inline asm → intrinsics. Correct, this holds.
- **`weak_alias` does NOT need an assembler at all.** Assembler
  *directives* (`.weak`, `.set`, `.globl`) are handled generically in
  `tccasm.c`, independent of the arch backend — confirmed by testing a
  `.weak`/`.set` pair with the stub (`TCC_TARGET_RISCV64`'s original
  94-line dummy) still in place. Only actual *instruction mnemonics*
  route to the (absent) arch assembler. My i386 reasoning didn't
  transfer.
- Codegen is already direct — `gen_le32()` writes instruction words
  straight to the output section, no textual assembly step.

Net: deleted `riscv64-asm.c` and never wrote `riscv64-tok.h`. The only
real remaining consumer of "assembly" is a handful of standalone `.s`
files (musl's `setjmp`/`longjmp`/`vfork`/`clone`/`__set_thread_area`,
our own kernel's boot/trap code) — handled via `.long <hex>` raw
instruction encoding (see below), not a parser.

## Intrinsics added

`__builtin_riscv_syscall` (reuses the ordinary C call path — RV64's C
ABI already puts the first 8 args in a0-a7, which *is* the Linux
syscall convention, so only the final instruction differs), plus
`csrr`/`csrw`/`sfence_vma`/`wfi`/`sret`/`read_tp`/`read_fp`/`write_tp`/
`fence_i` for privileged/kernel use. This is what let musl's
`syscall_arch.h` (previously 340 of 421 build errors) work with zero
source patch — just `#ifdef __TINYC__` routing to the intrinsic.

## Codegen bugs, riscv64-gen.c

**`store(!local)`** and **`unimp: large addend for global address`** —
both `tcc_error()` stubs upstream, both hit real code (`mallocng`,
`math/log.c`). Fixed: absolute-constant stores now materialize the
address via `lui`+`addi` into a scratch register; symbol-relative
stores always use PC-relative `auipc`+addend addressing rather than
routing through a GOT (which can't carry an addend) — correct for our
static-non-PIE-only scope; a dynamic-linking build would need the GOT
path restored.

**`libtcc1.c`**: `#error unsupported CPU type` for the GCC-libgcc
arithmetic helpers (`count_leading_zeros`, `umul_ppmm`, `udiv_qrnnd`,
etc.) — upstream only ships x86 inline-asm versions. Added portable C
implementations; RV64 has native 64-bit arithmetic, so these compile
to ordinary integer ops, no asm needed.

## Bug 1: register-mapping — `REG_IRET` used as a raw register number

`riscv_gen_read_tp()`/`read_fp()` let `gv(RC_INT)` allocate an
arbitrary scratch register for a dummy pushed value, emitted `mv
<that register>, tp`, then the caller in `tccgen.c` unconditionally set
`vtop->r = REG_IRET` regardless of what `gv()` had actually picked.
`REG_IRET` is `TREG_R(0)` — a TCC-internal logical register-class
index, numerically `0` — passed directly to the instruction encoder
instead of through `ireg()`, which is what actually translates it to
the real hardware register (`ireg(0) = x10 = a0`). Encoded `mv x0(zero),
s0` instead of `mv a0, s0`, silently discarding the value into the
architecturally-hardwired-zero register.

Found via QEMU instruction tracing (`-d in_asm`), not inspection —
traced the crash back through the call chain, found `mv zero,s0` at
the very first read_fp call site in `_start`, and it was immediately
obvious once seen. Fixed by routing both functions through
`ireg(REG_IRET)`.

## Bug 2: `.word` is 2 bytes in TCC, not 4 — every raw-encoded `.s` file was silently corrupted

The five musl riscv64 `.s` files that must be real machine code
(`setjmp`, `longjmp`, `vfork`, `restore`, `__set_thread_area`) are
generated by disassembling the real GNU-as output and re-emitting each
instruction as a raw encoded word — `tools/gen_asm_words.sh`, same
technique as the kernel's ISR-stub generator. The generator originally
used `.long 0x%s` — no wait, `.word 0x%s`. TCC's *generic* `.word`
directive (`tccasm.c`, shared across all targets) is 2 bytes, matching
historical x86/GAS convention — not RISC-V's 4-byte instruction width.
Every `.word 0xXXXXXXXX` directive silently truncated to its low 16
bits, and consecutive truncated halves concatenated into unrelated,
wrong 32-bit "instructions" once reassembled by the linker.

Confirmed precisely: `__set_thread_area`'s first instruction, `mv
tp,a0` (`0x00050213`), came out of the built object as `0x05130213`
(`addi tp,t1,81`) — an entirely different, nonsensical instruction.
Traced by recompiling the `.s` file standalone and comparing the
disassembly byte-for-byte against the source's own `.word` values
until the mismatch was undeniable, then confirmed against `tccasm.c`
source (`TOK_ASMDIR_word`/`short` share `size = 2`; only `TOK_ASMDIR_long`/
`int` are 4). This one cost the most debugging time in the whole port —
the failure mode (`a_crash()`, musl's own deliberate `*(volatile
char*)0=0` abort) looked identical to several *other* real bugs along
the way, so each required tracing to rule in or out.

Fixed the generator to emit `.long` instead of `.word`, regenerated all
five files from genuine pristine sources (re-fetched, not reconstructed
from memory).

## Bug 3: a naming mismatch silently defeated musl's own arch-override mechanism

Separately, and compounding the above: the generated files had been
named `<name>_words.S` (e.g. `__set_thread_area_words.S`). musl's
Makefile decides which arch-specific `.s`/`.S` file *replaces* the
generic C fallback purely by matching the **base filename** with the
`/riscv64/` path component stripped — `REPLACED_OBJS` in `Makefile`.
`__set_thread_area_words.o` stripped to `__set_thread_area_words.o`
does not match the generic `__set_thread_area.o`, so the override never
triggered: **both got compiled and archived**, and the linker picked
whichever came first alphabetically — the generic stub, which for
riscv64 (no `SYS_set_thread_area` syscall; TLS is purely the `tp`
register) is `return -ENOSYS`.

For `setjmp`/`longjmp` specifically this would have been silent and
much worse: musl's generic fallback there is a genuinely empty (0-line)
`.c` file. Every one of these five files was affected identically.

Found by testing `__set_thread_area` in complete isolation (a
hand-written `_start` bypassing `crt1`/`__libc_start_main` entirely,
since the normal path calls it automatically before `main()` ever
runs, which had been masking the bug as "crashes somewhere in
startup" rather than pointing at the real function). Fixed by renaming
all five files to their correct base names, matching what musl's
override logic requires exactly.

## A related generator gap, found while regenerating

`setjmp`/`longjmp` each define three aliased symbols at one address
(`setjmp`/`_setjmp`/`__setjmp`). `objdump -d`'s default per-address
annotation only shows *one* symbol name when several alias the same
address, so the original generator silently dropped two of the three
`.globl`s — undetected until the *next* rebuild produced "undefined
symbol 'setjmp'" at a completely different link (musl itself doesn't
call `setjmp` by name; a test program does). Fixed by pulling the
complete symbol table via `nm` instead of relying on `objdump -d`'s
address labels, and emitting a `.globl`+label pair for every name at
each address.

## Verified

`qemu-riscv64-static` running a TCC-compiled, musl-linked test program
covering `malloc`/`free`, `snprintf`, and a real `setjmp`/`longjmp`
round-trip through a separate function call — output `riscv64
musl+tcc sum=285`, exit 0 (both the arithmetic check and the
setjmp/longjmp check passed). This is the same bar as the original
i386 spike.

## Important scope clarification: what's actually proven vs. what isn't

Everything verified above — musl's full test suite, busybox's full test
suite — only ever needed our TCC as a **host tool**: compiled *on*
x86_64, generating riscv64 *target* code. That path is solid, exercised
heavily, and every bug found in it is fixed and documented above.

**TCC self-hosted for riscv64 — compiled by itself into a riscv64
binary, then actually run — is a separate, harder bar, and it is
NOT yet working.** `qemu-riscv64-static ./stage1/tcc -v` hangs (an
infinite loop, not a crash — no output at all, killed by timeout).
This is the riscv64 equivalent of the i386 port's P9 "TCC compiles
TCC" closure milestone, and it was never actually exercised during
the musl/busybox work above, which only needed stage0. Found late,
while setting up a unified dual-target Makefile modeled on the i386
one (whose own `selfcheck` target this hang was discovered through).

Given the severity of the time constraint at the point this was found,
it's being documented as a known open issue rather than chased further
right now. The most likely suspects, in rough order of likelihood, for
whoever picks this up: something in `riscv64-gen.c`'s handling of a
control-flow or function-call pattern that TCC's own source exercises
but the (comparatively simple) test programs used throughout this port
never did; or a stack-frame issue specific to larger, more deeply
nested functions than any test case here reached. Given this session's
track record (four real, subtle codegen bugs found in the more
thoroughly-tested paths), a fifth in less-tested territory isn't
surprising and doesn't undermine what's already verified — it's
scoped narrowly to "TCC running as a self-hosted riscv64 binary",
nothing else.

## busybox: also done, one more real gap found

Same targeted config as i386 (ash + core utilities), same `__GNUC__`
spoof, same `trylink` fixes (archive relisting, startfile scoping,
diagnostic-flag removal). Every `.c` file compiled clean on the first
attempt — the hard part was entirely in the musl layer above.

**One new gap, riscv64-specific: no `alloca()` at all.** i386/arm/
x86_64 satisfy it via a real linked runtime function
(`lib/alloca86.S` etc); no such file exists for riscv64, and — unlike
those architectures — there's no correct way to implement `alloca` as
an ordinary out-of-line function call at all: it has to grow the
*calling* function's own stack frame, which only the compiler,
emitting code inline at the call site, can do. This is also how GCC
and Clang actually implement `__builtin_alloca` internally, not as a
real call in optimized code.

Implemented as a proper compiler intrinsic (`riscv_gen_alloca` in
`riscv64-gen.c`, dispatched from a new `TOK_alloca` case in
`tccgen.c`): round the requested size up to 16 bytes, `sub sp, sp,
size`, return the new `sp`. Two real bugs surfaced building this,
each caught by testing before trusting the result:

- **A crash in TCC itself** (not the compiled program — the compiler
  process segfaulted), traced with `gdb` to `compare_types()`
  dereferencing a garbage `CType*`. Cause: constructing the `void*`
  result type by hand (`type.t = VT_PTR; type.ref = NULL`) instead of
  going through TCC's own `mk_pointer()` helper, which the type-
  comparison code assumes was used (a `VT_PTR` always needs a real
  `Sym` describing the pointed-to type, never `NULL`). Fixed by
  building a `VT_VOID` `CType` first and calling `mk_pointer()` on it,
  the same way every other pointer type in the compiler gets made.
- **`gfunc_epilog`'s stack-pointer restoration is a compile-time-fixed
  offset**, which `alloca` (permanently lowering `sp` to make room
  that must survive until the function returns) silently invalidates.
  Fixed by re-deriving `sp` from `s0` (the frame pointer, holding the
  function's entry `sp`, untouched by anything including `alloca`)
  instead of trusting `sp`'s current value — mathematically a no-op
  when `alloca` wasn't called, since `sp` already equals `s0 - v` at
  that point in that case. Deliberately scoped to the common small-
  frame case only (`v < 2048` bytes, the only case any real call site
  hits); the existing large-frame path does its own incremental `sp`
  adjustment that a second full restoration would double up on
  incorrectly, and getting that composition right wasn't worth the
  risk under time pressure given how many similar stack-frame bugs
  this session had already found. A function combining `alloca()` with
  more than 2KB of its own ordinary locals is a documented, narrow
  unsupported case, not a silent one.
- **musl's `<alloca.h>` does `#define alloca __builtin_alloca`**
  (expecting the compiler to recognize `__builtin_alloca` as a real
  builtin), which meant the intrinsic — hooked on the raw `alloca`
  token — never fired for any file that included it; busybox's actual
  calls all failed as an undefined external symbol at link time, not
  a compile error, so `.c` files still compiled clean while the final
  link failed. Fixed by predefining `__builtin_alloca` back to plain
  `alloca` for our target (`libtcc.c`, gated on `TCC_TARGET_RISCV64`),
  mirroring the same `__builtin_alloca -> alloca` predefine TCC
  already ships for FreeBSD and macOS.

Verified: a standalone test allocating 50, 17 (deliberately non-16-
aligned, to exercise the rounding), and 200 bytes via `alloca()` in a
helper function called three times from `main`, writing and summing
each buffer, confirmed exact correct sums (1225, 136, 19900) plus a
plain local variable in `main` still reading correctly afterward
(proving the caller's own frame wasn't corrupted by three rounds of
callee `alloca` + epilogue restoration). Then the full busybox
comprehensive test — the same battery as i386 (`ash` running real
pipe chains, `sed`, `grep`, `find`, `expr`, `sort`) — all correct under
`qemu-riscv64-static`.


## Still open

Kernel port not yet started (no Multiboot equivalent on RISC-V — needs
its own boot story, likely OpenSBI/SBI-based; CLINT/PLIC instead of
PIC/PIT; no GDT/segmentation at all, a different privilege model
entirely). Genuinely comparable in scope to the whole original i386
P3-P5 kernel effort, not a small follow-on.

TCC self-hosting for riscv64 (see above) — the stage1-hangs issue.
