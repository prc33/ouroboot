open This is now, by a wide margin, the single largest source of repository size and the most misleading part of the "kernel is 75,929 lines" headline number — 89.7% of that is five generated C byte-array headers for test fixtures, not kernel logic:

The mechanism to remove all of these already exists and is proven — it's exactly what already carried BusyBox and exec_target out of the tree: pack each fixture's ELF bytes into the tar the kernel already loads at boot (mm/tar.c, kernel/test/build-selfhost-initrd.sh is the current template) instead of running kernel/gen_user_test_header.py to turn them into unsigned char[] literals compiled by the kernel's own C compiler. Doing this for the remaining six fixtures removes essentially all 68,143 lines with no behavior change — the kernel already knows how to load, and BusyBox already proves the mechanism works with a real, larger ELF than any of these fixtures.

Target: kernel/ drops from 75,929 to roughly 7,800 lines — a 90% reduction — purely from this one change, using a mechanism that's already shipped and tested for a harder case.

2. Checkpoint-orchestrated boot

open kernel/riscv64_kmain.c (469 lines) still chains P1 through P10 as sequential drain-hook callbacks — 46 references to run_*_test/checkpoint in that one file. This is real, load-bearing test infrastructure, not dead code, but it means the "normal boot path" and the "development history" are the same code path, so nothing can change the boot sequence without touching every checkpoint after it.

Both prior reviews recommended the same fix, and it's still the right one: a direct boot path (init platform → mount initrd → create PID 1 from /init → schedule) as the product path, with P1–P10 preserved as a separate test-checkpoints style target rather than the thing every boot runs through. This doesn't reduce line count much on its own (checkpoints stay, just relocated/gated), but it does reduce coupling — right now no syscall or scheduler change can be made without reasoning about which checkpoint it might affect.

This is a coherent, working subsystem — not tangled into the RISC-V path (the READMEs and Makefiles already keep the two targets clean-room separate via TARGET=/ARCH=). That's exactly why both reviews called it the right kind of thing to archive wholesale (a tag or legacy/ branch) rather than simplify in place: there's nothing to simplify, it's just a second product that happens to double every "does this change break the other target" check. If i386 is being kept deliberately as a second proof point (the README's own "closure milestone is met" framing for i386 suggests it might be), this is a legitimate reason to keep it — but it should be a decision made explicitly, not a growing tax nobody revisits.

4. Compiler: preserve the language, trim the product

mostly keep The compiler is 41,072 lines now (was 38,624), the growth entirely explained by the new wasm32 backend (3,680 lines) that now builds the emulator. Both prior reviews' central and correct point still applies and deserves restating precisely, because it's easy to over-apply a "simplify" instruction here in the wrong direction:

Do not simplify: the preprocessor (tccpp.c, 4,062 lines), the parser/type system/codegen core (tccgen.c, 8,368 lines), or anything implementing standard C semantics (conversions, initializers, bit-fields, variadic functions, etc). These are the actual product. A smaller number here that comes from cutting language surface would violate the project's own stated goal of compiling standard C, not a project-specific dialect.

5. Kernel process/VM state — still the sharpest correctness-adjacent complexity

open, and worth flagging above pure line-count concerns: both prior reviews independently identified the same design gap, and this agent's own self-hosting work this week hit real bugs growing directly out of it (documented in git history: a hardcoded fork stack-clone window, and separately global brk/mmap cursors that let one exec'd process inherit another's heap bookkeeping). Per the changelog now in docs/self-hosting-todo.md, the brk/mmap-globals bug and the fork stack-window bug were both found and fixed as part of reaching the self-hosting closure — but they were fixed as point patches (per-process brk/mmap state added, fork's clone range made to track the real committed stack), not via the structural fix both reviews independently suggested: a small per-process VM-region list shared by the ELF loader, fork(), execve(), and brk/mmap, replacing the remaining hardcoded address windows. The specific bugs are gone; the shape that produced them — special-cased fixed windows instead of one region table — is still there, so a similar bug is one new syscall or one new codepath away from recurring.

6. Documentation: split, don't cut

open, unchanged since last review. 1,835 lines across 13 files, still one flat docs/ directory mixing the current architecture/plan documents with phase-by-phase development diary entries (kernel-p3-findings.md through kernel-p5-checkpoint2-findings.md, emulator-p1-findings.md, emulator-p3-findings.md). None of this needs to be shorter — it's exactly the "what broke and how it was diagnosed" record the README says is the point — but a reader looking for "how does this system work today" currently has to tell current design apart from historical narrative by filename convention alone. A docs/history/ subdirectory for the phase findings, leaving self-hosting-system-plan.md/riscv-port-findings.md/emulator-plan.md (or their eventual successors) as the current-state entry points, costs nothing and fixes this.

Priority order

Ranked by size of win versus risk of touching something load-bearing, given another agent is currently mid-work on the self-hosting closure:

  1. Move the six remaining test-fixture payloads into the initrd tar. Highest line-count win (68,143 lines), lowest risk — the exact mechanism is already proven for BusyBox and exec_target in this same tree. Should be close to mechanical.
  2. Decide, explicitly, whether i386 stays. ~8,944 lines and a standing "verify unaffected" tax on every shared-file change (this agent's own sessions have paid that tax repeatedly). If it stays as a deliberate second proof point, say so somewhere prominent (README already gestures at this) so it stops looking like unmaintained scope; if not, archive it in one commit.
  3. Give processes a real per-process VM-region list instead of hardcoded fork/exec address windows. Not primarily a line-count exercise — it's closing off the exact shape of bug class that was just hand-patched twice during the self-hosting work.
  4. Split docs/ into current vs. history. Cheap, zero risk, pure navigability.
  5. Direct /init boot as the product path, checkpoints demoted to a test target. Do this after (1)-(3) are stable, since it touches the same boot file the initrd migration and VM-region work will already be changing.
  6. Compiler product-surface trim (dynamic linking, debugger plumbing, embedding API) — lowest urgency, since none of it is actively causing bugs or blocking anything; do it once the higher-priority items free up attention, and only ever by removing product features, never language semantics.
